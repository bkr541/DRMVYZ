# Cinema 2.0 Mood Conductor

A shared conductor for Auto Performance. The Visual Director already reads the audio intelligence into a phase, an intensity, a momentum, a build and a section context, and the choreography runtime already turns music events into transient contributions. What was missing is one coherent, smoothed reading of **how the passage feels**, plus the **impact of a drop** that rises at once and decays, so a preset's whole look can move together instead of through a few unrelated accent rules. The Mood Conductor computes that, once per frame, for every preset.

Adopted so far by **Mainframe, Depth and Electric Storm** (their own Auto Performance toggle gates everything; no preset gained a parameter and no revision changed). Sound Drawing XY's conductors (`XyScopeWireConductor`, `XyScopeStandardPerformance`) are the same idea for that engine; this one is built on Cinema 2.0's own director and target runtime.

## What it is, and what it is not

- `cinema2/conductor/Cinema2MoodConductor.ts`. It reads **only** the shared audio-intelligence frame and the Visual Director's frame. It analyses no audio and has **no drop detector of its own**: a drop is `cinema2CanonicalDropEvents` (exported from the choreography runtime, which now uses the same function for its `drop` signal), and a phrase is `cinema2CanonicalPhraseEvents`. This keeps the rule in `cinema2-auto-performance.md`: no new analyzers or drop detectors.
- The runtime captures the mood right after the director and puts it on the frame (`frame.mood`, null whenever the director is, so with no analysed track or live features it is null and nothing is invented). `Cinema2Runtime.getMoodFrame()` exposes it for diagnostics. It holds still while the transport is paused (no time passes) and starts again on a seek, loop or track change.
- Deterministic: no randomness, a pure function of the frames and the time between them.

## The mood frame (`Cinema2MoodFrame`)

All 0..1, smoothed (fast to rise, slower to fall):

| Field | From |
| --- | --- |
| `energy` | director intensity (else track or overall energy) |
| `tension`, `complexity`, `brightness` | the audio features (brightness is the spectral centroid) |
| `build`, `momentum` | the director's build and momentum |
| `calm`, `drive`, `tense`, `peak` | the section's kind when the analysis has one (intro, verse, build, preDrop, drop, breakdown, bridge, outro), else the signal alone; they melt from one passage into the next |
| `shock` | jumps to the drop's strength (at least .75) on the frame a drop lands, then falls with a 1.7 s time constant |
| `activity` | .4 energy + .2 tension + .15 build + .15 momentum + .2 drive + .3 peak + .3 shock − .2 calm |
| `feel` | `peak` (peak or shock above .45), `tense`, `calm`, else `driving` |
| `section`, `drop`, `boundary` | the section id, type and progress; whether a drop landed; and the musical boundary of this frame (a drop, a section change or a phrase, in that order of authority) |

## Silence: "nearly off"

A stop in the music quiets the show. The Visual Director deliberately treats a "Silence or stop" marker as an *impact* (a dramatic moment), so the conductor does not use the marker. It gates itself on the **real signal level** (`audio.features.overallEnergy` and `rms`, whichever is higher):

- **Detect.** Below 0.03 for 0.3 s is a stop; it ends above 0.06 (the gap between the two stops it chattering). With no level evidence (features unavailable) it never claims a silence.
- **Gate.** `mood.silence` rises over 0.25 s and falls over 0.15 s. While it is up, `activity`, `peak`, `drive`, `tense` and `shock` are pulled out by **90%** and `calm` takes over (up to 0.9), so the feel reads calm even inside a drop section. The raw `energy`, `tension` and `build` still report what they report.
- **A drop ends a stop at once** and lands with its full shock.
- **Grid accents wait for sound.** The beat grid is time-based, so beat, downbeat and phrase events keep arriving through a silent stop. The new `not-silent` choreography condition (passes unless `mood.silence` is at least 0.5; passes when there is no mood) is on the beat-grid accent rules: Depth's beat, downbeat, phrase and build accents, and the shared Auto Performance build, pre-drop and bar-lift gestures (Electric Storm, Reactor, Threshold, GO-TO, Reliquary, War Of Worlds). Drops are not gated.

Example, a drop at full strength followed by 4 s of silence, from the conductor's real output (Electric Storm strikes, authored 0.58, and Depth rate, authored 1.10): before the stop 0.71 and 1.60; 1 s into silence 0.39 and 0.84; at the end of the stop 0.37 and 0.81, then 0.66 and 1.49 within 0.3 s of the music returning. In a stop the values go **below** the authored ones (calm takes away), not merely back to them; the preset's own audio reactions are already near zero in true silence.

## Two ways a preset uses it

**Continuously, as choreography sources.** Twelve new continuous paths: `mood.energy`, `.tension`, `.build`, `.momentum`, `.complexity`, `.brightness`, `.activity`, `.calm`, `.drive`, `.tense`, `.peak`, `.shock`. `createCinema2MoodRules` (and `withCinema2MoodDrives` for a manifest, or the `mood` field of a `withCinema2AutoPerformance` spec) turns a list of drives into gated rules:

```ts
{ id: 'rate', target: cinema2AutoTargets.module('depth-tunnel', 'rate'), source: 'mood.activity', operation: 'add', value: 0.7 }
```

`add` contributes `value × source` (negative values take away); `multiply` scales from ×1 to ×`value`. The contribution is transient: the authored value is the baseline and is never rewritten, the target runtime clamps the result to the control's own range, drives that share a source become one rule, and the rules exist only while the preset's Auto Performance toggle is on (and scale by its reactivity or intensity control, so a control at zero silences them). With the toggle off the preset is identical to one without the conductor (a test checks this for Electric Storm).

**Discretely, through `Cinema2MoodChooser`.** For choices among a preset's own options (patterns, programs, looks): it changes only on a musical boundary, holds a choice at least `minHoldSec` (4 s) unless a drop lands, never repeats the current choice, and picks by a hash of the track and the boundary, so the same track gives the same show. It does nothing without a mood frame.

## Pattern Change and Trigger

With Auto Performance on, the **music** chooses whether the preset changes pattern and how often; the saved Pattern Change and Trigger are *never rewritten* and come straight back when the toggle goes off. `Cinema2MoodFrame.pattern` is `{ patternChange, trigger, reason }`, or `null` when there is no beat grid (then the saved values stand). `resolveCinema2PatternControls(saved, mood, autoEnabled)` gives a preset the effective values.

**Trigger** is a ladder, slowest to fastest: `bar8, bar4, bar, beat2, beat`. The starting rung comes from the passage's feel: calm 0, driving 1, tense or peak 2. Then it moves up: +1 while the build is above 0.5 (+2 above 0.75; it falls back at 0.45 / 0.7 so it does not flutter), +1 while the drop's shock is above 0.5 ("impact"), +1 in the last 15% of a non-calm section ("approach"). Changes are debounced (0.5 s of agreement, at least 3 s between changes), except a drop, which moves immediately.

**Pattern Change** is on while there is sound, and **off in a silent stop** (silence of 0.5 or more), which holds the current pattern until the music returns.

Depth advances through its rotation (Sparse, Chase, Orbit, Gate Pulse, Alternating Frames, Portal Relay) on the chosen trigger, only while the music has Pattern Change on, with the special programs (discharge for drops and builds, full pulse in a quiet moment, portal relay at a high level) taking over for their moments. Without a mood frame it keeps its old 16-beat rotation. Mainframe feeds the effective values to its trigger identity, pattern controller and Auto Performance chooser. Both modules get them from the shared `Cinema2PatternControlResolver` (see "Adopting it in a preset"). Mainframe's `inspect()` reports `effectivePatternChange`, `effectiveTrigger` and `patternControlsAutomatic`. Other pattern presets (Backstreet and the rest) do not use it yet; they adopt it with the three steps below.

The inspector shows the choice under the two controls ("Auto Performance is choosing: On, Every 4 Bars for a driving passage"), polled like the live slider values. The saved toggle and dropdown keep showing what the user saved. The ladder's thresholds are a first guess for tuning on real tracks.

### Adopting it in a preset (three steps)

1. **Manifest.** Add `patternControls: { patternChange, trigger }` to the preset's `withCinema2MoodDrives({ ... })` spec (the Auto Performance toggle is the spec's `enabledParameter`). This tags the three parameters with `metadata.moodPolicy` (`patternChange`, `trigger`, `autoPerformance`), keeping any metadata they already had, and works even with an empty `drives` list. Never write the tags by hand: `tagCinema2MoodPolicies` throws on an id that is not in the manifest.
2. **Module.** Own a `Cinema2PatternControlResolver<MyTriggerId>`, call `update({ saved: { patternChange, trigger }, mood: frame.mood, autoPerformance })` once per frame before the usual trigger-event logic, act on the returned `patternChange` and `trigger` instead of the saved ones, add `...resolver.inspect()` to `inspect()`, and `reset()` it with the module. `autoPerformance` is the toggle, already combined with anything else that must hold (Mainframe adds "is playing"). The module keeps its own event identity, debounce and pattern logic; only the two inputs change.
3. **Nothing in the inspector.** The "Auto Performance is choosing" line finds the tagged controls by their tags (`findCinema2PolicyControls`), so no panel code is needed.

The compiler enforces it (`validateCinema2MoodPolicyParameters`): each tag sits on the right kind of control (`patternChange` and `autoPerformance` on booleans, `trigger` on an enum), the Trigger offers every value the music may choose (`bar8, bar4, bar, beat2, beat`, all in the canonical Trigger list), each tag is used once, and the three are tagged together. A preset that fails any of these does not compile, so it cannot half-adopt and silently never show or use the choice. A preset that tags nothing is unaffected.

A preset's pattern-by-feel lists (Mainframe's `Cinema2PatternAutoPerformance` `mood: { options }`) are separate and optional: they pick among the preset's own patterns, so each preset supplies its own.

## Seeing what Auto Performance is doing

Contributions never rewrite a saved value, so a slider's thumb and readout keep showing what the user saved (that is what dragging edits). The Cinema 2.0 Design inspector therefore shows the **live** value too: a second readout ("2.00 →" before the saved "1.10") and a yellow marker on the slider's track, for every numeric control whose live value differs from the saved one by more than 0.4% of its range. It reads what the renderer reads: `resolveCinema2LiveValues` resolves each module or effect target bound to the control (the parameter's own target is the saved value), polled about eight times a second and only re-rendering when something changes. `SliderRow` takes an optional `liveValue`; without it nothing about the slider changes. Any preset with drives gets this for free.

A note on Depth: **choosing a Pattern (or turning Pattern Change on) turns Auto Performance off** (the parameters carry `userEditSetParameters`), so after picking a pattern the toggle has to be switched back on for any of the drives to act.

## Adding it to another preset

1. Pick the targets that should move with the passage and a baseline-relative drive for each (`add` or `multiply`, a source, a value).
2. For a preset with `withCinema2AutoPerformance`, add a `mood: [...]` list to the spec. For one with its own toggle (Depth, Mainframe), wrap its manifest with `withCinema2MoodDrives({ idPrefix, enabledParameter, strengthParameter?, drives })`.
3. For a preset with Pattern Change and a Trigger, add `patternControls` to that spec and use the resolver in the module (see "Adopting it in a preset"). For a preset with a pattern controller, also give `Cinema2PatternAutoPerformance` a `mood: { options }` config and pass `mood`, `deltaTimeSec`, `basePattern`, `patternChange` and `seed` from the module frame (see the Mainframe module).
4. Keep the revision; add tests in the style of `Cinema2MoodConductorPresets.test.ts` (the twin-engine differential: the same music into the preset with the toggle on and off).

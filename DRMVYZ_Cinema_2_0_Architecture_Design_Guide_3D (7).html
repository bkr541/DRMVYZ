Cinema 2.0 is being created because the current DRMVYZ visual stack has outgrown the historical distinction between Shader Scene / Shader Pad presets and Cinematic Worlds. Existing Cinema already provides a strong runtime foundation, but it currently acts as both an engine and a compatibility host for two legacy preset models. That arrangement preserves substantial functionality while creating duplicated ownership across musical interpretation, post-processing, history, cameras, parameter UI, and preset-specific behavior.

●
CURRENT-STATE FINDING

Current Cinema has a real graph/runtime foundation with single WebGL ownership, compiled execution, render-target management, camera support, capability-aware controls, effects, media and lifecycle handling. The primary problem is fragmented responsibility layered on top of that foundation, not an absence of capability.

Cinema 2.0 therefore exists alongside Cinema 1 rather than rewriting it in place. The target combines Reactor-level rendering sophistication, Electric Storm-level musical interpretation, Afterhours-style hierarchical show direction, and first-class 3D/spatial architecture through one common preset model.

◆
ARCHITECTURE DECISION

Cinema 2.0 is a sibling engine with one native preset contract. It selectively reuses proven low-level Cinema infrastructure while intentionally refusing to make permanent Shader Scene or Cinematic World compatibility part of the new engine contract.

Goals & Non-Goals

The boundaries that keep Cinema 2.0 powerful without becoming a game engine.

Architectural goals

CINEMA 2.0 TARGET DESIGN
  • One top-level preset model that spans simple fullscreen shaders through complex 3D audiovisual worlds.
  • Shared infrastructure for rendering, history, effects, cameras, lighting, media, parameters, resources and diagnostics.
  • One authoritative Audio Intelligence contract that preserves meaningful music-analysis capability instead of collapsing it prematurely.
  • First-class musical direction: Audio Intelligence describes music, Visual Director interprets visual significance, and preset choreography selects the creative response.
  • First-class 2D, 2.5D, procedural, media-driven and 3D composition without privileging one rendering technique.
  • Schema-driven Inspector/UI placement and capability truth with no named-preset branches in generic UI code.
  • Explicit resource ownership, failure isolation and frame-time budgeting suitable for live VJ operation.
  • Extensibility through modules/effects/rigs without creating a universal mega-interface or a new mini-engine per preset.

Non-goals

  • Cinema 2.0 is not intended to become a general-purpose game engine.
  • It will not require every preset to use 3D, lighting, depth or advanced attachments.
  • It will not eliminate custom Shader code or genuinely preset-specific procedural algorithms.
  • It will not permanently emulate every Cinema 1 preset contract inside the native runtime.
  • It will not force all creative behavior into declarative data when custom module code is clearer.
  • It will not expose arbitrary preset-owned UI layouts or untracked GPU allocation.

RECOMMENDATION

Preserve single-context ownership, safe activation, compiled execution, capability filtering, diagnostics and deterministic cleanup as implementation assets. Do not preserve adapter-specific ownership boundaries as the Cinema 2.0 preset model.

Where the current canonical Cinema frame preserves, collapses, or loses upstream music intelligence.

Phase 1 verified that the upstream Music Intelligence frame contains richer information than the canonical Cinema frame. Electric Storm

The current musical-intelligence reference and the intent-to-geometry separation worth preserving.

Electric Storm is the current musical-intelligence reference. ElectricStormWorld owns an Audio Choreographer, Strike Generator and Thunder Controller. The Audio Choreographer interprets prepared music into semantic strike intents; the Strike Generator owns spatial candidate generation and anti-repeat behavior; Thunder independently schedules atmospheric illumination. The final Shader turns strike impact into lightning, branching and screen-space shake/zoom.

Current Cinema supports genuine extruded OpenType text and SVG geometry, GPU mesh caching, transforms, depth-tested drawing and shared-camera integration.       Audio Contract

      Performance

      Frame-time, GPU memory, resource, media, Shader, switching, and graceful-degradation guardrails.

      ⌁
      LIVE PERFORMANCE REQUIREMENT

      Cinema 2.0 is live VJ software. Frame-time budgeting, GPU memory accounting, safe preset switching and graceful degradation are architecture requirements, not post-launch optimization tasks.

      At 60 FPS the total frame budget is about 16.67 ms, but Cinema 2.0 cannot assume it owns the entire interval. Initial engineering targets should aim for approximately 10–12 ms typical GPU visual cost and 2–3 ms Cinema2 CPU update/submission cost, with real measurements on representative hardware becoming authoritative.

      Cost domainGuardrail

      HistoryExpose memory cost; prefer reduced resolution where visually acceptable
      Depth/aux attachmentsAllocate only when capability requires them
      EffectsCost hints and quality variants; optional pass bypass
      GeometryTrack vertices, indices, instances, draw count and materials
      ParticlesDeclared maximum capacity and current active count; quality can lower capacity

      Preset switchingPrewarm next preset; atomically switch only when safe
      Quality degradationReduce expensive effects/volumetrics/particles/secondary scales before removing core identity

      DECISIONS · ARCHITECTURE GUIDE

      Final Recommendations

      Recommended implementation order and the immediate next action.

      1. Build Cinema 2.0 as an isolated sibling engine. Do not mutate Cinema 1 into the target architecture while it is still the production safety net.
      2. Start with the minimal native Shader path and schema-driven Inspector before implementing advanced systems. Simplicity is the first architecture gate.
      3. Use Reactor 2.0 to prove Render Graph and History Service, then use it to pressure-test the single-writer choreography model.
      4. Introduce the rich Audio Contract, Visual Director and Choreography Engine before porting Electric Storm so the most musically sophisticated reference preset validates shared significance rather than recreating another private director.
      5. Generalize Afterhours laser geometry only after it can serve a second rig. Do not mistake successful extraction from one preset for a reusable API.
      6. Add shared 3D through a measured vertical slice: model loading, core materials/lights, depth, camera integration and Aether Temple. Defer expensive optional capabilities until the frame budget proves room for them.
      7. Treat compatibility migration and creative enhancement as separate milestones. Native Cinema 2.0 should earn its catalog selectively.
      8. Make ResourceManager, diagnostics, prewarming, failure isolation and quality degradation non-negotiable before broad preset migration.
      9. Retire legacy adapters only when their valuable presets have been intentionally migrated or left behind, not because Cinema 2.0 has reached an arbitrary milestone.

      Begin implementation Phase 1 with a separate cinema2 engine registration/runtime shell and isolated store. The first acceptance test is not a sophisticated visual: it is repeated Cinema1 ↔ Cinema2 switching with safe cleanup and no behavioral change to Cinema1.

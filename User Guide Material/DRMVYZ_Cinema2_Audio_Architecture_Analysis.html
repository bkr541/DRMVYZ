System review  /  Audio Intelligence  /  Cinema 2.0

One audio source.
Many decision gates.

The Cinema 2.0 presets do not each run their own Web Audio analyser. They share the Audio Engine, canonical Music Intelligence processing, a central AudioFeatureBus, and a read-only Cinema 2.0 bridge. What varies is the acceptance of incoming frames, the rules that turn musical facts into visual actions, and the conditions that permit those actions to play out.

Primary conclusion

The past failure was a missing publication step between Web Audio and AudioFeatureBus in the Cinema 2.0 host. This meant no real audio frame reached the preset, regardless of brightness settings or lighting logic. The uploaded version contains a Stage-side analyser pump, but its correct operation under every source/transport combination still needs runtime validation.

How this architecture developed: the repository maintains multiple visual-engine families (legacy Cinema, Cinema 2.0, Canvas, PixGrid, and others) and renderer-owned analysis pumps. These separate host/rendering models explain much of the different routing behavior. Exactly why earlier developers made each decision cannot be proven from code alone; this is the most plausible architectural interpretation of the existing implementation.

What is a Web Audio analyser?

An AnalyserNode measures the incoming sound. It provides raw frequency levels (low to high) and waveform samples. It is the measurement instrument, not the musical brain. In DRMVYZ, the shared audio engine creates master and L/R analysers, along with separate reference analysers and other taps.

What is Audio Intelligence?

The MusicIntelligenceEngine turns samples into normalized sub/bass/mid/high energy, kicks/snares, rhythmic events, signal confidence and, when available, track-informed sections, phrases, builds and drops. The AudioFeatureBus is where these interpreted facts are published for consumers.

A live analyser does not automatically mean a valid musical event exists. The measuring, interpreting, publishing, accepting, triggering and drawing stages are separate.

Six checkpoints that can silence a preset

03 / FAILURE SURFACES
GATE 01Source availabilityWas a source actually connected? Was the AudioContext created and the analyser present?
GATE 02Sampling permissionDoes the host call the frame pump? Is analysisActive true? Does this publisher have authority?
GATE 03Frame deliveryWas an updated frame published? Is its identity/time valid? Did the bridge capture it?
GATE 04Runtime acceptanceDoes Cinema 2.0 expose the frame to the preset, or replace it with null?
GATE 05Event and timeDo transport, pause, animationActive, capabilities, and event deduplication allow change?
GATE 06Visual outputDid module parameters reach material/shader updates? Is Master Intensity, emission and render state valid?

A screen can remain static if any one checkpoint fails. Increasing emissive brightness tests only the last checkpoint and cannot repair the others.

What actually happened to Mainframe

07 / INCIDENT RECONSTRUCTION

The earlier conversation establishes the incident sequence. The current ZIP establishes which elements of the proposed fix exist today. The historical diagnostic report itself is not included in full in the supplied message, so the exact historical payload has not been independently re-verified.

01 / VISIBLE SYMPTOM

Mainframe circuits, logo and indicators stayed dark

Brightness multipliers were raised in the native module and Three scene renderer. This adjusted final illumination values, not the system carrying music into the renderer.

02 / DIAGNOSTICS ADDED

Opt-in Mainframe diagnostic report

The debug mode added records for transport identity, frame acceptance, musical cues, lighting values, WebGL readiness and errors. It revealed a repeated audio: null state in the previous test.

03 / ROOT CAUSE DESCRIBED

Consumer existed, publisher was missing

Cinema 2.0 was capturing AudioFeatureBus frames without sampling the shared master Web Audio analyser. No new sample meant the downstream pipeline lacked meaningful current musical information.

04 / PATCH PRESENT IN UPLOADED ZIP

Stage now calls MusicIntelligenceAnalyserFramePump

Cinema2Stage.tsx constructs react:cinema2 pump and samples it from the transport's getState() when analysisActive && analyser. ReactView.tsx passes its shared analyser and Music Intelligence track identity to Stage.

Remaining inconsistency and risk areas

08 / CODE FINDINGS
CONFIRMED DESIGN DIFFERENCE

Mainframe is a special case in the shared runtime

Cinema2Runtime.ts gives Mainframe independently validated audio even when analysisActive disagrees with certain transport flags. Other presets receive audio only when the host's analysisActive flag is true. That is real architectural divergence, not just different choreography.

CONFIRMED DESIGN DIFFERENCE

Visual time still uses a shared host gate

The runtime sets animationActive = analysisActive && !paused. Thus Mainframe's special ability to accept a frame does not automatically allow its visual clock to advance while the host analysis flag is false.

HIGH-PRIORITY COMPATIBILITY RISK

Live Input: analysisActive can be true while playing is false

useAudioEngine.ts intentionally stops file transport during microphone capture. Mainframe's playback resolver declares playing:false as stopped, while After Hours also guards some musical triggers using playing !== false. Their live-input musical-event behavior needs a focused test.

DATA-GOVERNANCE RISK

Publication metadata and partial updates are distinct

AudioFeatureBus.setFrame() is publisher-gated; updatePartial() is a separate, ungated shallow merge. Cinema 2.0 reads the latest publication metadata, which may reflect a lyrics/metadata partial update rather than the latest full analyser publication. Track/publisher attribution deserves review.

BEHAVIORAL RISK

Event qualification varies by preset

Some effects require an actual musical event, some use Director authority, some fall back to beat clocks, and some require Auto Performance/BPM Sync or a specific trigger mode. A preset can have legitimate bands while a structural cue is unavailable.

OBSERVABILITY GAP

Debugging remains Mainframe-centric

Mainframe includes targeted debug reports, rejected-frame reasons and rendering status. Equivalent one-click per-preset evidence of "input → eligibility → action → output" is not uniformly surfaced across the examined modules.

QA / REGRESSION RISK

Cross-preset parity is not the same as isolated tests

Different module tests can each pass while host analysis ownership, track identity, seek and source-switch paths still disagree. A real cross-preset acceptance harness is needed.

CONFIRMED CORRECT SEPARATION

Visual diversity belongs downstream

Reactor's shader mappings, Electric Storm's strike generator, Interlock's LED state and Mainframe's circuit/lighting adapter are good reasons for differing visual behavior. They are not good reasons to duplicate raw audio detection.

The architecture I would standardize

09 / RECOMMENDATIONS

The goal is one authoritative musical truth, one consistent delivery contract, many artistic interpretations. Do not remove useful preset-specific choreography or visuals to force all presets to look or behave alike.

P0 · 01

Make AudioFeatureBus publisher authority explicit per source

One owner samples the active analyser; all renderers become consumers. Preserve the dedicated live-input owner. Document who publishes file/demo frames and what happens during a renderer switch.

P0 · 02

Use one source-aware runtime playback/analysis contract

Separate: sourcePresent, audioAnalysisAvailable, transportPlaying, transportPaused, musicReactive, and animationActive. Do not assume microphone analysis must have a playing file transport.

P0 · 03

Unify frame validity checks across Cinema 2.0

Check fresh full-frame publication, identity, reset/seek behavior and signal availability once in the bridge/runtime. Move Mainframe's special-case rules into a general policy, with explicit allowances rather than preset-name branching.

P1 · 04

Keep events canonical, keep visuals distinct

Use shared kicks, beats, bars, phrases, drops and event IDs. Allow presets to choose their own targets, envelopes, pattern logic and intensity. Avoid local re-detection of musical structure.

P1 · 05

Instrument the same six checkpoints for every preset

Create a common diagnostic report showing analyser availability, publisher, frame age, acceptance reason, gated events, effective parameters and render/material readiness.

P1 · 06

Test a shared source/transport matrix

File playing, file paused, stopped with loaded track, seeking, loops, track changes, renderer switches, demo, live microphone and analyser failure. Verify both event semantics and visible pixel/brightness deltas in WebGL.

P2 · 07

Define silence and fallbacks per capability

No invented "drops" from realtime BPM. Make it explicit which visuals remain ambient when structural analysis is absent, and which require genuine events. This preserves musical honesty without leaving all presets black.
